# NXP `.106` Oracle Validation — Test Plan

**Status:** All phases executed 2026-08-01 (0, 1, 2, 2e, 3 — results below, inline). Phase 3 reached a real topology blocker rather than the originally planned live-key-byte capture; see that section for what's still open if resumed. New tools produced: `bin/muram-mmap-dump.py`, `bin/kg-scheme-read.py`.
**Follow-up (2026-08-05):** the Phase 3 topology blocker was **solved** by the successor plan (`plans/NXP-106-DEEP-DIVE-PLAN.md` Phase B — netns + ingress-interface-keyed policy routing, TTL-verified genuine 3-hop transit through `.106`). That test also produced a decisive negative result: `cmm`'s connection table and all 6990 `/proc/fqid_stats/pcd/*/*` counters stayed at zero across three TCP flows through the verified transit path — root-caused to `cmm`'s vendored static libnetfilter_conntrack 1.1.0 (+comcerto-fp patch) never invoking `__cmmCtCatch()` (zero CT-TRACE events across every boot Aug 1–5; `specs/conntrack-root-cause-analysis.md` + qdrant "cmm-root-cause-CORRECTED"). **Practical consequence for this plan's methods: `/proc/fqid_stats/pcd/*/*` is NOT a usable HIT/MISS oracle on `.106`'s current build** — use the direct register/MURAM reads (`bin/kg-scheme-read.py`, `bin/muram-mmap-dump.py`) this plan produced.
**Board:** `.106` — genuine NXP vendor ASK 1.x stack (`cdx.ko`/`fci.ko`/`auto_bridge.ko`, `cmm`, `dpa_app`, `fmc`), `nxp-sdk` branch/flavor. Contrast with `.185`, which runs the from-scratch ASK2 rewrite (`dpaa1` branch) this project has been debugging.
**Why this board:** `.106` is a *working* hardware-offload implementation on the same silicon (FMan v3, 210.10.1 microcode). Every open question in `specs/cc-comparator-compare-window-hypothesis.md` and the undocumented-gap notes in `arch/fman-microcode-210-programming-reference.md` is, on `.106`, a question with a real, currently-true answer sitting in live hardware state. This plan is a set of read-mostly tests to extract that answer instead of continuing to reverse-engineer it from `.185` failures.

**Ground rule:** `.106` is a reference oracle, not a test mule — its value is being a known-good, unmodified vendor stack. **Prefer read-only observation. Do not reflash, reconfigure `cdx.ko`, or rebuild its kernel unless a phase explicitly says so and the user has separately approved it.** Every phase below is annotated with a risk level.

## Phase 0 — Recon (read-only, zero risk) — EXECUTED 2026-08-01

Purpose: establish ground truth about what's actually running on `.106` before trusting any inference from source code or old qdrant notes. Several existing docs already contain unresolved contradictions this phase should settle.

- **0a. Stack health — DONE.** `ask-check` on `.106`: **40/42 OK, 0 FAIL** (2 WARN are unused physical ports `eth1`/`eth2`, unrelated). Full ASK 1.x pipeline confirmed live: `cdx.ko`/`fci.ko`/`auto_bridge.ko` loaded, `cmm` running (`ls1046a-ask.service`), FMan microcode 210.10.1 + PCD initialised, `/dev/cdx_ctrl` present, `/proc/fqid_stats` populated.
- **0b. Real `fmc` path confirmed live, not the stub.** `journalctl -k`: `start_dpa_app::calling dpa_app argv ...` → `cdx_module_init::start_dpa_app successful`. `dpa_app`/`fmc`/PDL/XML files all present per `ask-check` item 10. The `dpa_nofmc.c` stub is not in play.
- **0c. STRICT_DEVMEM — RESOLVED, and the original framing was wrong.** `CONFIG_STRICT_DEVMEM` is confirmed **disabled** (`# CONFIG_STRICT_DEVMEM is not set`) on **both** `.106` and `.185` via live `zcat /proc/config.gz`. A `dd if=/dev/mem` read at each board's real MURAM physical address (`.106`: discovered via `/proc/iomem` → `fman-muram` at `0x01a00000`; `.185`: same base address, `0x01a00000`, under the parent `1a00000.fman` resource) fails identically on **both boards** with `dd: error reading '/dev/mem': Bad address` — while a `dd` read at a real `System RAM` address succeeds cleanly on both. **Root cause is not STRICT_DEVMEM at all**: `/dev/mem`'s `read()`/`write()` syscalls require `pfn_valid()` (normal system RAM only) on this kernel; MURAM is memory-mapped I/O/SRAM, which is only reachable via `mmap()` on `/dev/mem` — a completely different code path, unaffected by `STRICT_DEVMEM` here. `bin/ask-pcd-regdump.py` already uses `mmap()` (confirmed by reading its source) and is not blocked by this on either board. **Doc corrected:** `plans/ASK2-MASTER-PLAN.md` §1.3a.
- **0d. Debug surface — larger than source reading found.** Confirmed `/proc/fqid_stats/{tx,rx,pcd,sa}/<fqid>` as expected, but also found (missed by static source analysis, since it's registered dynamically by the sdk_fman driver, not obvious from a source grep): **`/sys/devices/platform/soc/1a00000.fman/fm_kg_regs`** (live KeyGen global-control register dump), `fm_fpm_regs`, `fm_plcr_regs`, `fm_prs_regs`, `fm_regs`, per-port `fm_port_regs`/`fm_port_bmi_regs`/`fm_port_qmi_regs` for all 22 ports, and a `statistics/` directory with parser/KeyGen/policer hardware counters (`pcd_kg_total`, `pcd_prs_*`, `pcd_plcr_*`). `fm_kg_regs` dump captured: only the fixed global registers (`fmkg_gcr`, `fmkg_eer`, `fmkg_ar`, etc.) — **per-scheme registers (`KGSE_EKFC` etc.) are not directly memory-mapped** and still require the indirect access-register (`fmkg_ar`) + shadow-window protocol to read a specific scheme, which this sysfs node does not expose. A follow-up tool would need to drive that protocol itself (via `mmap()` on the FMan CCSR block) — not yet built.
- **0e. Live extraction config captured — high-value result.** `/etc/cdx_pcd.xml` on `.106`, distribution `cdx_tcp4_dist`: field key is `ipv4.src(4) → ipv4.dst(4) → ipv4.nextp(1) → tcp.sport(2) → tcp.dport(2)` = 13 bytes, **identical field set and order to dpaa1's old `EKFC=0x001C0006` (pre-PORT_ID)**, plus `<combine portid="true" offset="16" mask="0xF"/>` appending a 4-bit port-ID byte (`keysize="14"` total) because the table is `shared="true"` across ports. Full analysis and its implications: `specs/cc-comparator-compare-window-hypothesis.md` §5a. Also confirmed structurally load-bearing: `hashtable external="yes"` on this classification — `.106`'s working TCP4 HIT path genuinely uses the same external-hash silicon mechanism this project's `arch/fman-microcode-210-programming-reference.md` models, not a different one. **Note:** dpaa1's current target EKFC is `0x801C0006` (14 bytes with PORT_ID prefix), not `0x001C0006`.

**Follow-on finding surfaced by 0e, checked against dpaa1's own code (not board-tested, static grep):** dpaa1's FE-VM chain (`pcd->fe_vm_chain_built`, `bin/kernel-fixups/F_090.py`/`F_092.py`) is built **once per `pcd`, shared across every port that engages** — the same sharing pattern NXP's `shared="true"` config has, but without NXP's port-ID disambiguation byte. This does **not** explain F-157/F-158's decisive negative (that test armed a single port only), but is a real multi-port correctness gap worth fixing before any future multi-port ehash test. See `specs/cc-comparator-compare-window-hypothesis.md` §5a for the full note.

But the doc's "after key: 4B next-FE MURAM offset" row is this project's *own* design, not vendor-documented — the real `flags` field packs `OPC_OFFSET`/`PARAM_OFFSET` bits pointing to a **per-entry embedded opcode chain** (the same opcode set as the manip/forward chain). A separate, unrelated field `kgHashShift` is explicitly marked obsolete in the same struct; don't conflate the two. Recorded in §10.2a.

## Phase 2 — Live idle-state MURAM dump (ioctl, low risk, read-only) — EXECUTED 2026-08-01, partial result

Purpose: read the actual programmed CC/hash-table state on `.106` without generating any traffic yet.

- **2a. Dump tool built — but the planned ioctl path doesn't work on the currently-deployed `.106` image.** `CDX_CTRL_DPA_GET_MURAM_DATA` (`_IOWR(0xbe,4,struct muram_data)`, confirmed present and correctly wired in `cdx_dev.c`'s `cdx_ioctl_table[]` on the `nxp-sdk` branch source, gated by `#ifdef DPAA_DEBUG_ENABLE`) was tried first. The exact `_IOWR` command number was hand-verified byte-for-byte against the source macro before calling it live. Result: `journalctl -k` showed `cdx_ctrl_ioctl::unsupported ioctl cmd c010be04` — the **running kernel module does not have this ioctl compiled in**, meaning the deployed `cdx.ko` on `.106` predates, or was built without, `DPAA_DEBUG_ENABLE` — a real discrepancy between this repo's current CI config and what's actually flashed. **Pivoted to `mmap()` on `/dev/mem`** at the MURAM physical base (`0x01a00000`, confirmed disabled `STRICT_DEVMEM` per Phase 0c) — the same technique `bin/ask-pcd-regdump.py` already uses. This worked cleanly: full 393216-byte (384 KiB) MURAM captured in one call, no errors. Tool: `bin/muram-mmap-dump.py` (to be committed).
- **2b. Group-table location: attempted, inconclusive — do not trust these specific hits.** Pattern-searched the dump for the CONT_LOOKUP AD signature (`word2 = 0x40000000 | ((keySize-1)<<24)`) using the exact keysizes known from Phase 0e's live `cdx_pcd.xml` (10, 38, 8, 20, 34, 12, etc). Found 11 matches — but decoding them produced implausible `numKeys` (67–128) and `matchTableAddr`/`adTableAddr` values far outside the 384 KiB MURAM range (e.g. `0xfc0a00`), and one hit's preceding bytes decode as readable ASCII (`"CE=1"`). **These are false-positive byte-pattern coincidences, not real AD tables** — most likely landing in the per-entry embedded opcode/parameter data found in Phase 1 (§10.2a), which is dense, semi-structured, and large enough to produce chance 32-bit matches. A blind pattern search without a real anchor is not reliable in a densely-populated 384 KiB region; do not repeat this specific approach without a genuine pointer first.
- **2c/2d — blocked on a reliable anchor.** Confirmed a different real MURAM offset exists in kernel logs (`FM_PCD_Init::... offset 3f508`, within the captured range, for "ext timers" — not our target, but it validates the addressing/capture is sound) — this is not itself the pointer needed. The reliable path is reading a live KG scheme's `KGSE_CCBS` register directly (see new Phase 2e below), not guessing from the dump content.

### Phase 2e — per-scheme KG register read via the `fmkg_ar` indirect protocol — EXECUTED 2026-08-01 (approved), real findings

`fm_kg_regs` (Phase 0d) only exposes fixed *global* KeyGen registers. Per-scheme content (`KGSE_EKFC`, `KGSE_CCBS`, etc.) requires the indirect access-register protocol: write a scheme-select+read-request command to `fmkg_ar`, poll for completion, read the resulting shadow-window registers. This is a register **write** (to trigger a read, not to persist any config change) — approved by the user before attempting it.

**Protocol source: this project's own in-tree mainline driver**, not re-derived from documentation guesswork — `work/linux-6.18.34/drivers/net/ethernet/freescale/fman/fman_keygen.c` (`keygen_write_ar_wait()`, `build_ar_scheme()`) defines the exact bit constants (`FM_KG_KGAR_GO=0x80000000`, `FM_KG_KGAR_READ=0x40000000`, `FM_KG_KGAR_SEL_SCHEME_ENTRY=0x00000000`, `NUM_SHIFT=16`, `FM_KG_MAX_NUM_OF_SCHEMES=32`) and `struct fman_kg_regs` layout (shadow window at local offset `0x100`, `fmkg_ar` at `0x1FC`). Physical base confirmed via `/proc/device-tree/soc/fman@1a00000/keygen@c1000` (`reg = 0xc1000 0x1000`) → `0x01a00000 + 0xc1000 = 0x01ac1000`. Tool: `bin/kg-scheme-read.py` (to be committed) — read-intent only (`FM_KG_KGAR_READ`, never `FM_KG_KGAR_WRITE`), scans all 32 scheme slots.

**Result:** ran cleanly, zero errors/timeouts across all 32 scheme reads. 12 schemes enabled (0–11), 20 empty. All 12 enabled schemes show `kgse_mode = 0x8X000006` — **AC_CC mode, confirming `.106` uses the same dispatch mode this project's own architecture settled on (2026-07-16).**

**Real, decisive structural finding: `kgse_ccbs = 0x00000000` for every single enabled scheme.** This means the CC group-table MURAM pointer is **not** stored in the KeyGen scheme registers at all when using AC_CC mode — `kgse_ccbs` is specifically the pointer field for **CCBS mode** (`next_engine=2`), a different dispatch mode this project tried and abandoned in favor of AC_CC (2026-07-06 course-correction, already in project history). In AC_CC mode, the group-table pointer instead lives in the **per-port** `FMBM_RCCB` BMI register — confirmed real, non-zero, plausible values found on 5 ports via the already-known `fm_port_bmi_regs` sysfs node: `0x00048a00`, `0x00048b00`, `0x00048c00`, `0x00048d00`, `0x00048e00` (sequential, 256 B apart — exactly the pattern a per-port table allocation would produce, unlike the earlier Phase 2b false positives).

**Decoding the content at those RCCB offsets did not cleanly match this project's CONT_LOOKUP AD model.** Reading `w0..w3` at MURAM offset `0x48a00` from the Phase 2 dump gives `w2=0x04020808` — not the expected `0x40000000 | ((keySize-1)<<24)` pattern (top byte `0x40-0x6X`). **This is reported as an open, unresolved discrepancy, not forced into an interpretation.** Two live hypotheses, neither yet checked: (a) `FMBM_RCCB`'s raw register value needs a bit-mask or scale transform before use as a byte offset (this project's own `arch/fman-microcode-210-programming-reference.md` doesn't document `FMBM_RCCB`'s exact encoding, only `FMBM_RCCB`'s *role*), or (b) AC_CC-mode dispatch on this SDK generation targets a different AD species entirely — the `en_exthash_node`/`t_ExtHashFe`-style descriptor referenced in earlier project history (2026-07-06 LSDK reference analysis, `FM_PCD_FE_TYPE_EXT_HASH=0x06000000` in the type field) rather than a bare `CONT_LOOKUP` group table. **Next step if resumed:** decode `FMBM_RCCB`'s bit layout from the DPAA RM directly (not inferred), or cross-check `w0`'s top bits against the `t_ExtHashFe` type-field encoding already on file.

## Phase 3 — Live traffic HIT capture (mutating: requires real offloaded traffic) — EXECUTED 2026-08-01, blocked on topology, not attempted further

Purpose: the decisive test. Capture the actual byte content of a genuinely hardware-matched flow key, on hardware known to be dispatching HITs correctly — something this project has never had on `.185`.

**Topology constraint discovered before any traffic was sent:** both `.106` and `.185` are dual-homed directly on *both* test subnets (`.106`: `eth3=10.99.1.106/24`, `eth4=10.99.2.106/24`; `.185`: `eth3=10.99.1.185/24`, `eth4=10.99.2.185/24`). Neither board needs the other as a gateway for L3 reachability between the two subnets — there is no natural third-party host for `.106` to genuinely *forward* traffic to. This is the standard "3-node 10G test plane" topology (built for `.185`'s own offload throughput testing), not a router-under-test topology.

**Two traffic patterns tried, both minimal and fully reverted (only ever touched `.185`'s live kernel routing table via plain `ip route add`/`del` — never VyOS's persistent config, never `.106` at all):**

1. **Temporary `/32` route on `.185`** (`10.99.2.200 via 10.99.1.106 dev eth3`) to a nonexistent address, then `ping` + a TCP connection attempt from `.185`. Result: `.106` genuinely received and attempted to route the packets (confirmed — ICMP `Destination Host Unreachable` replies came *from `.106` itself*, which only happens after a real forwarding/ARP-resolution attempt), but `cmm -c 'show stat connection query'` stayed at **0 active connections** and the full `/proc/fqid_stats/pcd/{eth3,eth4}/*` counter set showed **zero diff** against baseline. Route reverted immediately after.
2. **Temporary `/32` route on `.185`** (`10.99.2.106 via 10.99.1.106 dev eth3`) to `.106`'s own real `eth4` address, forcing the path via `eth3` instead of `.185`'s direct `eth4` connection — this succeeds at the TCP level (`nc -zv 10.99.2.106 22` → `succeeded!`, a genuine handshake). Still: **0 active connections**, **zero fqid diff**. Route reverted immediately after.

**Conclusion (not a failure, a real structural finding):** both tests confirm `cmm`'s flow-offload path and the monitored PCD classification FQIDs are specific to genuinely **transit/forwarded** traffic — packets `.106` routes *through* itself to a third party — not to locally-terminated traffic (test 2) and not to traffic that fails to reach any real destination (test 1), regardless of which physical interface it arrives on. This is logically consistent with `cmm`'s documented role (accelerate the *forwarding* decision) and rules out "any packet touching eth3/eth4 shows up in these counters" as a valid assumption for future test design.

**3b–3d (confirm-HW-dispatch, diff-MURAM, read-key-bytes) were not reached** — they require a successfully classified, genuinely-forwarded flow with a real reply, which needs either a third physical/virtual host on one of the two test subnets, or a more invasive setup (temporary dummy interface/network namespace acting as a responder) than this plan's minimal-footprint approach covers. **Flagging this as the concrete blocker for anyone resuming Phase 3**, rather than force an inconclusive result by improvising further against the reference board without a clearer plan.

## What this plan deliberately does not attempt

- No re-flash, no `cdx.ko` reconfiguration, no kernel rebuild for `.106`. If Phase 2/3 turn up a need for kernel-side instrumentation (e.g. the vendor driver doesn't log what's needed), that's an escalation requiring a custom-instrumented build of `.106`'s kernel — explicitly out of scope here because it risks the one thing that makes `.106` valuable: being an intact, unmodified reference.
- No attempt to make `.106`'s EKFC/FMC scheme match `.185`'s `EKFC=0x801C0006` — they're different extraction configurations by design; this plan uses `.106` to validate the *mechanism model*, not to directly transplant a byte layout onto `.185`.
