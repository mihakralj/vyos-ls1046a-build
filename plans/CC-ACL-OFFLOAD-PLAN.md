# CC Match-Walker as ACL / ntuple / tc-flower Hardware Backend — Plan

**2026-09-05 · dpaa1 · Companion to `plans/OFFLOAD-CAPABILITY-PLAN.md` and `plans/ASK2-MASTER-PLAN.md` §4.6. Supersedes the stale verdict in `plans/CC-TREE-REBUILD-PLAN.md` (see §1).**

## 0. Purpose and scope

Every capability in `plans/OFFLOAD-CAPABILITY-PLAN.md` today is a **flow accelerator**: it mirrors an already-classified, already-tracked kernel object (a conntrack entry, a bridge FDB row, a VLAN sub-interface) into an exact-match FMan ehash record. None of them do general packet classification against operator-authored rules with masks, ranges, or priority — a stateless ACL, a `tc filter ... flower` rule with a wildcarded field, or an `ethtool -N` steering rule are a structurally different problem: the rule set is static and operator-installed rather than derived from live connection state, and matching must handle "don't care" bits, not just a fixed 5-tuple.

This plan scopes hardware-accelerating that different problem using the FMan Coarse Classification (CC) engine's masked-key match-walker (`decomp/out/01-cc-match-walker.c`; RM §5.12/§8.7.4), across three kernel-facing surfaces:

1. **`ethtool -N` (rxnfc) steering rules** — a CC-tree bridge for this already exists (`kernel/common/patches/board/0109-dpaa-ethtool-ntuple-cc-steering-bridge.patch`, active in the series). Its status is unknown, not broken — see §1.
2. **`tc filter ... flower`** used as a standalone classifier (drop/redirect on a static rule, not flow-tracked) — currently unsupported; the existing `TC_SETUP_CLSFLOWER` handler in `kernel/ask/oot-modules/ask/ask_flow_offload.c` only accelerates already-matched flows and ignores `flow_rule` masks entirely (`ask_parse_match_v4`/`_v6` read `m.key` only, never `m.mask`).
3. **nftables netdev-hook hardware offload** (`nft ... flags offload` on an `ingress`-hook chain) — as of the kernel this project ships, nft's own hardware-offload lowering goes through the *same* `flow_cls_offload`/`ndo_setup_tc(TC_SETUP_BLOCK)` contract as tc-flower. This is not a fourth integration surface; it rides on whatever (2) builds.

So concretely this is two build efforts sharing one CC-tree builder, not three: **(A) validate/extend the existing ntuple bridge**, and **(B) build a static-rule ACL path on top of the tc/flow_offload block callback**, distinguishing it from the existing flow-acceleration path in the same callback.

## 1. Current state — read this before writing any code

**The 2026-08-05 verdict in `plans/CC-TREE-REBUILD-PLAN.md` ("CC-tree classification: no confirmed HIT, architecturally broken, do not patch further") is stale and does not apply to this plan.** That verdict was about a specific graft mechanism — `fman_pcd_kg_port_attach_cc()` writing the CC-tree pointer into KeyGen's `KGSE_CCBS` register — which five vendor-verified register fixes (F-159 through F-162) still could not make dispatch. The real problem, found afterward: AC_CC-mode silicon reads the CC-tree base from the **per-port BMI `FMBM_RCCB`** register, not `KGSE_CCBS`; `next_engine=2` (what the old graft used) is a confirmed no-op, and the correct `next_engine=3` / mode `0x80000006` encoding existed in the codebase but was wired only into the FE-VM/ehash arm path.

That has since been fixed and **proven working on silicon**, just not by finishing the old plan — by a different, later patch chain (`0118` reverted the broken CCBS graft after it caused a port stall; `0121h-fman-cc-miss-fe-production-api.patch` and `0121j-fman-pcd-hm-vlan-route-translate.patch` landed the corrected `FMBM_RCCB` graft and a working CC-miss-leg-to-`FE_ENTER` handoff). The proof is VLAN pop/push (`ASK2-MASTER-PLAN.md`, 2026-08-26, commit `36bf83de`): a per-port CC key dispatches into a combined VLAN-edit + L2-rewrite + IPv4-forward HMTD, with the CC-miss leg falling through to the existing ehash root (`fman_pcd_fe_root_get_offset()`). R5b (no-wrong-forward, PCP/DEI, MTU sweep, 100× churn, zero error frames) and full gate-off regression both passed. This ships default-off via `set interfaces ethernet ethN offload vlan`.

The generic CC-node API this success is built on is real and reusable: `fman_cc_tree_install(fm, port_id, tree)` / `fman_cc_tree_destroy(fm, port_id)` (patch `0098`), operating on `struct fman_cc_static_tree{ num_keys, miss_fe_off, keys[] }` / `struct fman_cc_key{ ethertype, proto, src_ip, dst_ip, src_ip_mask, dst_ip_mask, src_port, dst_port, target_fqid, hm_handle }` (`kernel/ask/oot-modules/ask/ask_vlan_cc.c`). Its current only caller (`ask_vlan_cc.c`) hardcodes `src_ip_mask = dst_ip_mask = 0xffffffff` — exact match only — by choice, not by hardware limit: masks are a first-class field in the struct and in the CC table row format.

**The ethtool ntuple bridge (patch `0109`) is the single highest-value fact this research turned up, and it's the required first step:** it already implements `ETHTOOL_SRXCLSRLINS`/`SRXCLSRLDEL`/`GRXCLSRLALL`/`GRXCLSRLCNT` in `dpaa_ethtool.c`, backed by the same `fman_cc_tree_install()`, and it is active in the series today (not archived). It predates the `0118`/`0121h`/`0121j` graft fix — but because it only calls the shared install function rather than implementing its own graft, it most likely inherited the fix transparently. **Nobody has re-tested it since.** Its status is genuinely unknown: not proven broken, not proven working. Before designing anything new, Phase 0 (§3) settles this on real hardware, the same way RX checksum and RX hash were settled earlier in this project's history — with a kprobe/traffic capture, not by reading code.

Hardware capacity, for sizing later phases: RM §8.7.4 puts the CC-node key limit at 255; the software cap (`FMAN_CC_MAX_STATIC_KEYS`) is 64 (raised from 32 by `0121k-fman-pcd-cc-max-keys-64.patch`) — a software choice, not silicon's. `specs/fman-keygen-flow-key-spec.md` §6.1.4 estimates ~8 CC nodes fit in the 64 KiB MURAM arena (~12.3 KiB/node fully populated) → roughly 2000+ hardware-resident rules if ever scaled that far, far beyond what a stateless ACL or ntuple rule set realistically needs.

There is no vendor oracle for this capability: the real NXP stack's own CC usage (`decomp/vendor-vs-ask2-offloads.md`) is flow-classification dispatch for its conntrack-mirroring `cmm`/FPP daemon, not general ACL/firewall offload. This is the first capability in the catalog with no reference implementation to diff against — design decisions here are this project's own, not a port of vendor behavior.

There is no per-rule hardware stats plumbing today. `ask_debugfs.c`/`ask_stats.c` have zero CC-related counters; `ask_vlan_cc.c` states outright that CC nodes have no stats AD on this microcode without `AllocStatsObjs`, which hits a MURAM allocation wall (`ASK2-MASTER-PLAN.md` line 346) and is deferred, unrelated to this plan. Decomp's `CC_ENTRY_STATS_EN`/per-key stats bit (`decomp/out/01-cc-match-walker.c`) is real silicon capability that this project currently has no software path to read back. Treat per-rule hit counters as an explicit non-goal until that upstream blocker clears (§6).

## 2. Governing constraint

`plans/OFFLOAD-CAPABILITY-PLAN.md` §4.6.1 (binding, inherited from `ASK2-MASTER-PLAN.md`): the kernel is the single source of truth for object lifetime — here, `tc`/`nft`/`ethtool` rule state, not any driver-side shadow copy — and `ask.ko`/the driver "MUST mirror only offloadable objects into hardware"; anything unsupported (a mask shape the hardware path can't express, a resource-exhausted CC tree) must fail closed to the kernel's own software classifier, never silently drop traffic or block the `tc`/`ethtool`/`nft` command. Concretely: an insert that can't be expressed in a CC tree returns success from the *kernel's* perspective (rule installed, enforced in software) and just doesn't set `TCA_CLS_FLAGS_IN_HW` / returns `-EOPNOTSUPP` from `set_rxnfc` gracefully, mirroring how `ask_parse_match_v6` already falls back to software for unsupported IPv6 flows today.

This also fixes a design question that would otherwise be ambiguous: CC-tree ACL rules are **not** tracked as a new ASK2-owned state model. They mirror whatever `tc`/`nft`/`ethtool` already tracks; `ask.ko`/the driver holds only the hardware-resident mirror (as `0109`'s `priv->cls_rules` list already does for ntuple) and rebuilds it from callback events, never invents rule lifecycle of its own.

## 3. Phase 0 — validate the existing ntuple bridge on silicon — DONE, PASSED (2026-09-05)

Verified on `.185`, eth3, real traffic from the `.116` peer, same kprobe/live-traffic methodology already used earlier this session for the RX checksum and RX hash verification.

- `ethtool -N eth3 flow-type tcp4 dst-ip 10.99.1.185 dst-port 5303 action <queue>` was accepted (`ethtool -n eth3` echoed it back correctly) and traced end to end: `dpaa_set_rxnfc` → `dpaa_cls_reinstall` → `fman_cc_tree_install` → `fman_port_set_cc_base`, every call returning success (`retval=0`). `fman_port_set_cc_base` is the actual BMI register write (`FMBM_RCCB`) — the exact register `CC-TREE-REBUILD-PLAN.md` identified as the one the old `KGSE_CCBS` graft never touched. It executes and succeeds today.
- Behavioral proof, not just API success: kprobing `rx_default_dqrr`'s second argument (`struct qman_fq *fq`, `fqid` field at offset `+0x18`, fetched via raw register syntax `+24(%x1):u32` after `$argN`/BTF-name fetch args turned out unsupported on this kernel) and comparing two otherwise-identical fixed-size (512 KiB) TCP transfers from `.116`: the rule-matching flow (dst-port 5303, `action 3`) landed overwhelmingly on **FQID 512**; an unmatched flow (dst-port 5306, no rule) landed overwhelmingly on **FQID 287** — a different, KeyGen-hash-selected default queue. Two distinct real FQIDs for otherwise-identical traffic, gated purely by the ntuple rule, is direct ground truth of hardware steering, not an inferred proxy. (A first attempt used CPU-core affinity from the trace as a proxy signal — inconclusive, since NAPI/portal CPU affinity did not shift as expected between queue targets. Abandoned in favor of reading the real FQID directly; note this for future verification work on this driver, the CPU-proxy approach doesn't reliably indicate FQ steering here.)
- Rule was removed and all kprobes torn down afterward; `.185` returned to its pre-test state (`ethtool -n eth3` shows 0 rules).

**Conclusion: patch `0109`'s ethtool ntuple → CC-tree bridge is confirmed working on real silicon today, using the current (post `0118`/`0121h`/`0121j`) graft mechanism.** Phase 1 is extension work (masks, drop, priority) on a proven-working foundation, not a rescue of a broken one.

## 4. Phase 1 — ethtool ntuple: real masks, drop action, priority

Contingent on Phase 0 passing.

- **Mask granularity — INVESTIGATED + FIXED (patch `0193-fman-pcd-cc-key-mask-passthrough.patch`, not yet board-tested).** Read `cc_pack_key()` directly from a staged tree with the full patch series applied (`git worktree` + `git apply --3way` through `0192`, since the current byte layout had moved since patch `0108`'s original diff — it's now `PORT_ID(1)|SIP(4)|DIP(4)|PROTO(1)|SPORT(2)|DPORT(2)`, per F-190). The composite **is** byte-aligned; `0109`'s "KG composite is not prefix-aligned" reasoning was wrong. The real gap: `struct fman_cc_key.src_ip_mask`/`dst_ip_mask` were already declared and documented ("prefix-style mask") but `struct fman_pcd_cc_hw_key` (the internal translation target) had no mask fields at all, and `cc_pack_key()` hardcoded `msk[]=0xff` for every byte of a participating field regardless of what mask was requested — the mask was silently dropped two layers before reaching MURAM. Patch `0193` adds `src_ip_mask_be`/`dst_ip_mask_be` to the hw-key struct, wires them through `dpaa_cc_key_to_hw()` (defaulting to exact-match `0xffffffff` when unset, so every existing caller — `ask_vlan_cc.c`, `0109`'s own exact-match rules — stays byte-identical), writes them verbatim into the CC row in `cc_pack_key()`, and relaxes `0109`'s `dpaa_cls_validate()`/`dpaa_cls_reinstall()` to accept and forward a real mask. Touches no NIA/register/graft logic — purely which mask bytes land in the already-working match table. Ports/tos stay exact-or-wildcard only (no established ACL use case yet for partial port masks; deliberately out of scope for this pass).
- **Drop action — INVESTIGATED, DEFERRED (do not implement without further gating).** Reading the current `cc_write_leaf_ad()` (post-`0115`/`0116` SDK-convergent rewrite) found the situation is riskier than the mask question: LS1046A errata A006675/SW006 means **every** CC leaf AD must exit through the FM_CTL `PRE_BMI_ENQ_FRAME` ucode fixup (NIA `0x28`) to release per-frame task state before the BMI enqueue — `cc_write_leaf_ad()` only ever emits that path today (fqid enqueue or RSS fall-through), and the raw `BYPASS`-type NIA (`0xc0000000`) present in the *original* `0108` diff no longer exists in the current code; it was removed. A qdrant check on this session found the closely-related historical incident directly: the global `tfene=RELEASE` TX-confirm bypass (patch `0136`/F-108) leaked one `skbuff_head` per forwarded frame and required a real fix (per-port no-confirm TX FQ) — the same *family* of problem (bypassing the mandatory per-frame cleanup ucode) that a naive raw-BYPASS leaf AD risks reproducing as task-pool exhaustion / port death requiring reboot. **Do not add real hardware drop without first determining whether the FM_CTL AC-code space has a "discard-with-cleanup" variant of `0x28`** — that's a register-level research question for whoever picks this up next, gated by AGENTS.md §S0 same as any other NIA-level change. Until then, `RX_CLS_FLOW_DISC` stays rejected exactly as `0109` already does.
- **Priority — CONFIRMED already correct, no work needed.** `dpaa_cls_reinstall()` keeps `cls_rules` sorted by `location` and does a full tree rebuild (not append) on every insert/delete.

**Board-tested 2026-09-05 (CI run `33978703626`, image `2026.09.05-1642-rolling`, deployed to `.185`).** Two distinct findings, one resolved and one new/open:

1. **`0193`'s software logic is confirmed correct.** Kprobing `fman_cc_tree_install()`'s actual `tree` argument (reading the real `struct fman_cc_key` fields going into the call, not just `ethtool -n`'s echo) showed `src_ip=0x0a630174` (10.99.1.116) and `src_ip_mask=0xffffffff` populate exactly as intended for an exact-match rule, and non-zero partial values populate correctly too. The mask-passthrough mechanism itself works as designed.

2. **A real ethtool(8) CLI gotcha cost significant time and is worth recording so nobody re-derives it:** `ethtool -N`'s `m MASK` argument is NOT the mask value you'd naively expect. `ethtool-6.1/rxclass.c`'s `rxclass_get_mask()` stores `~MASK` (bitwise NOT) for every field type including `OPT_IP4`, while `rxclass_get_val()` defaults an *unspecified* mask to `0xFFFFFFFF` directly (no inversion) whenever a bare value is given. Net effect: omitting `m` (or giving only a value) means "exact match"; explicit `m 255.255.255.255` actually means "wildcard everything" (ignore every bit); explicit `m 0.0.0.0` means "exact match" (redundant with omitting it); a real `/24`-style CIDR match requires `m 0.0.0.255` (inverted from the netmask you'd intuitively type, e.g. NOT `m 255.255.255.0`). `ethtool -n`'s displayed mask is *also* inverted back for display, so the round-trip looks deceptively "normal" — this is what caused an initial false read of a src/dst swap bug that turned out to be nothing more than typing masks the intuitive-but-wrong way. **Anyone testing this bridge by hand must remember: type the ethtool `m` value inverted from a normal netmask.**

3. **New, deeper, pre-existing bug found (not caused by `0193`, not yet root-caused):** even with the software struct 100% correctly populated end-to-end (point 1), an exact-match `src-ip` rule does **not** actually restrict which frames get steered on real silicon — traffic from a source IP that should be excluded (verified with `src-ip 10.99.1.116 m 0.0.0.0`, i.e. genuinely exact-match-only, tested against traffic from the *different* address `10.99.1.106`) still steers to the rule's target FQID. Only `dst-port` participation was ever confirmed to genuinely filter (Phase 0's finding). This means the CC composite's SRC_IP byte range (documented as bytes 1-4 of the 14-byte EKFC layout, F-190) isn't actually reaching the hardware comparator the way `cc_pack_key()`/the software assumes — a silicon/EKFC-extraction-alignment question in the same family as F-159 through F-190, not a `cc_pack_key()` or `0193` bug. **This predates `0193`**: the original `0109` code had the identical participation-gate logic (`if (m->ip4src) { ... }`), just with the mask always hardcoded to `0xffffffff` — it would have hit this exact same silent-non-filtering behavior for any src-ip-based rule, had anyone tested one before this session (Phase 0 only ever varied dst-port).

**Next step for whoever continues this:** root-cause finding 3 before trusting src-ip/dst-ip filtering for anything (ACL correctness depends on it). Suggested approach, mirroring this project's own established methodology (F-159/F-183/F-190): capture the REAL KeyGen-extracted composite bytes live on `.185` for a frame whose 5-tuple is known, and compare byte-for-byte against what `cc_pack_key()` writes as the expected key — the same class of technique that resolved the EKFC layout disputes documented in `plans/CC-TREE-REBUILD-PLAN.md`. Do not assume dst-ip has the same bug as src-ip (or the opposite) without testing it directly — this session confirmed dst-ip's *value* populates correctly in software but never tested whether it *behaviorally* filters either.

## 5. Phase 2 — tc-flower / nft netdev-hook static ACL

Contingent on Phase 1's CC-tree builder (masks + drop + priority) being real and tested.

- **Classifying which flower rules are "ACL" vs "flow acceleration."** Both arrive at the same `dpaa_setup_tc` → registered flow-offload-handler callback (`ask_flow_offload_setup_tc`, patch `0145`'s registration slot). They need to be told apart: a rule installed by `nf_flow_table_offload_setup()` (kernel-driven, tracks a live connection, uses `TC_SETUP_FT`) is the existing exact-match path and must keep going through `ask_flow_offload.c`/ehash unchanged. A rule installed directly by `tc filter add ... flower` (operator-driven, arrives as `TC_SETUP_CLSFLOWER` via `TC_SETUP_BLOCK`, not `TC_SETUP_FT`) with a mask or a bare drop/accept action and no flow-tracking intent is the new ACL case and should route to the Phase 1 CC-tree builder instead. Get this dispatch rule explicit and tested with both rule shapes before writing the CC-side integration — misrouting a flow-acceleration rule into the static-ACL tree (or vice versa) is a correctness bug, not just a missed-optimization.
- **nft netdev-hook offload** (`flags offload` chains) needs no separate driver code beyond what handles (2) — verify this experimentally with a real `nft` ingress-hook rule once tc-flower ACL works, don't assume it from kernel source alone.
- Reuse Phase 1's mask/drop/priority CC-tree builder; extend `struct fman_cc_key`/`ask_vlan_cc.c`'s tree-building code (or a sibling module, TBD by whoever implements this) rather than forking a third copy of CC-node management logic — there would then be three callers (VLAN, ntuple, tc-ACL) of one builder, which is the right shape per §2's "one intent, one builder" principle already governing the rest of ASK2.

## 6. Explicit non-goals for this plan

- **Per-rule/per-key hardware hit counters.** Real silicon capability (`CC_ENTRY_STATS_EN`), no software path exists (`AllocStatsObjs`/MURAM blocked, unrelated to this work). `tc -s filter` / `ethtool -S` reporting for hardware-offloaded ACL rules will show zero or software-estimated counts until that separate blocker clears — call this out in whatever CLI help text ships, don't silently under-report.
- **CIDR masking beyond what Phase 1 proves feasible.** If the KeyGen composite genuinely can't preserve byte alignment for partial prefixes without a new EKFC scheme, don't build that new scheme speculatively inside this plan — land exact-or-wildcard-per-field first (matching `0109`'s current real capability), file the CIDR gap as follow-on work.
- **A fourth integration surface for iptables/nftables *without* `flags offload`.** Software-path nftables/iptables rules are unaffected by this plan; only the explicit hardware-offload request path is in scope, consistent with "fail closed to software" in §2.
- **Resurrecting the legacy ASK 1.x CC-node patches** (`0014`/`0019`/`0026`/`0056`/`0057`, archived pre-6.18.34) or the excluded FE-VM patches (`0127`–`0138`). Both are superseded by the active `0086b`/`0098`/`0121k` family this plan builds on; no part of this plan needs them.
